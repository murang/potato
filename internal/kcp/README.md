# KCP 生命周期补丁

当前决定保留内部补丁，保证监听器在进程内停止时，尚未被 `Accept` 的会话也能完整回收。仅关闭 UDP socket 或框架已经接入的连接，不能替代这项保证。

## 来源和保留原因

本目录来自 [github.com/xtaci/kcp-go v4.3.4](https://github.com/xtaci/kcp-go/tree/v4.3.4)，对应 Go 模块版本 `v4.3.4+incompatible`，保留原 [MIT 许可证](LICENSE)。只复制运行时源码，除 `sess.go` 的监听器生命周期补丁外，其余复制的源码保持原样。

上游在收到 UDP 包后创建会话、注册全局 updater，再将会话放入待接收队列。此时框架可能还没有调用 `Accept`，会话也尚未进入 Manager。上游 `Listener.Close()` 不负责逐个关闭这些会话，因此仅停止监听会留下会话引用和定时更新工作；反复创建和停止监听器可能累积残留。

2026-10-21 核对的上游 [v5.6.73](https://github.com/xtaci/kcp-go/tree/v5.6.73)，提交 `bca9394563771f95b2c1d89cd15178227aaaa949`，仍存在这一问题。此前真实 UDP 复现中，监听器拥有底层 socket，4 个客户端各发送有效 KCP 包，服务端不调用 `Accept`；关闭监听器和客户端、等待 1 秒并执行 GC 后，会话计数仍比基线多 4，内部会话表及待接收队列也仍各有 4 项。该结果只针对上述版本和场景，不代表未来版本的状态。

暂不采用以下替代方式：

- 只在框架监听器记录已 `Accept` 的连接，会遗漏待接收会话。关闭后循环 `Accept` 也不能可靠判定队列已空，因为错误分支和取连接分支可能同时就绪。
- 包装 `PacketConn` 并使用 `ServeConn`，仍需补齐停止交付数据包、确认最后一个包已处理、可靠排空队列和解除 `Accept` 阻塞的同步机制。它依赖上游收包时序，复杂度不再明显低于当前补丁；升级到 v5 时还需处理 Linux 批量 I/O 绕过包装或被禁用的风险，性能影响尚未实测。
- 本项目的 `go.mod replace` 不会被引用 potato 的下游模块继承，无法保证修复随库生效。独立 fork 可以移走本仓库的源码，但仍需维护同一补丁。

框架允许进程继续运行时停止监听器，不能默认依靠进程退出回收资源。保留副本的代价是需要持续核对上游变更，而不是获得了自动升级能力。

## 补丁范围

功能修改集中在 [sess.go](sess.go) 的 `Listener` 生命周期：

- `Close` 使用 `sync.Once` 保证幂等，停止监听并关闭 UDP socket；它本身不负责逐个关闭会话。
- `monitorDone` 在收包循环退出时关闭，表示此前最后一个 UDP 包已处理完，不会再产生新会话。
- 新增 `Shutdown`：先调用 `Close`，等待 `monitorDone`，在锁内获取会话快照，再在锁外逐个调用 `UDPSession.Close`，最后排空待接收队列。锁外关闭避免与会话关闭时移除监听器记录的锁冲突。
- `Shutdown` 使用 `sync.Once` 保证重复调用安全；[框架 KCP 监听器](../../net/listener_kcp.go) 的 `Stop` 调用它，覆盖已接收和尚未接收的会话。

会话关闭会解除该会话在 updater 中的注册；全局 updater 本身仍可服务其他监听器和会话。补丁不修改 KCP 协议算法、加密、FEC、发送更新算法或调优参数，不在此目录混入候选性能优化。

## 兼容性和性能边界

- 框架的 `IListener`、`Session` 方法签名、`net.Conn` 接口及 KCP 包格式不变；已验证上游 v4.3.4 Go 客户端在本机 UDP、无加密和 FEC 的配置下与补丁服务端互通，其他客户端或配置需分别验证。
- **底层具体 Go 类型发生变化。** `Session.Conn()/Raw()` 返回的 KCP 连接属于 `github.com/murang/potato/internal/kcp`，不能再断言为外部 `github.com/xtaci/kcp-go.UDPSession`；直接接收外部具体类型的函数也不能直接接收它。下游不能直接导入该 `internal` 包，应依赖 `net.Conn` 或所需方法组成的接口。外部包的全局统计对象也不会自动统计内部包的会话。
- `Stop` 会关闭该监听器的全部会话，包括未交给 Manager 的会话；这不是等待所有待发消息送达的 graceful drain，不增加消息交付保证。
- 正常收发不新增逐包锁、轮询或消息复制。额外状态按监听器分配，停止时需要遍历会话并临时保存会话指针，成本随存活会话数增长；未单独量化该关闭阶段的耗时。

## 切回上游的条件

仅当以下条件满足后，才移除内部副本并切换到明确固定的上游版本：

1. **上游提供等价的完整回收能力。** 源码确认修复已进入目标版本，或公开接口足以在不访问私有字段的情况下实现完整关闭：停止创建新会话，等待最后一个包处理完成，关闭已接收和待接收会话，并解除阻塞的 `Accept`。仅有发布说明或 `Listener.Close()` 返回成功不够。
2. **生命周期回归验证通过。** 覆盖未 `Start` 即停止、从未 `Accept`、待接收队列积压或满载、接收与停止并发、重复停止、同进程反复创建和停止。核对会话、队列引用及定时更新注册回到预期基线，没有残留增长、死锁或数据竞争；同时验证 Manager 的会话关闭和回调完成时序。
3. **接口和协议兼容性验证通过。** 根模块及 example 编译、相关测试和 race 检查通过；验证原版 Go 客户端及项目实际使用的其他客户端，包括大包分片、消息顺序和关闭场景。检查 `Conn()/Raw()` 的具体类型、可选方法及统计对象变化；若迁移到 `/v5`，一并检查模块路径、最低 Go 版本和传递依赖要求。
4. **升级没有引入未评估的流程或性能变化。** 保留当前流模式及 KCP 参数，核对调度和收发实现差异；涉及这些路径时，在代表性负载及目标平台上比较 CPU、分配、吞吐和停止耗时，尤其检查 Linux 批量 I/O。发现明显退化时应先解决或明确接受取舍。
5. **迁移能随库正常分发。** 使用独立下游模块引用 potato 验证，不依赖下游额外配置 `replace`、修改模块缓存或构建时打补丁；完成后更新依赖和兼容性说明，再删除内部副本。
